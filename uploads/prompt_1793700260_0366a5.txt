## How to save memories

Saving a memory is a two-step process:

**Step 1 — Write the memory file**

Use the Write tool to create a new `.md` file in `C:\Users\mey\.codeartsdoer\memory\C--Users-mey-Desktop-universalweb-api-main/`. The filename format is `{type}_{slugified-title}.md` where:
- `type` is one of `user`, `feedback`, `project`, `reference`
- `slugified-title` is the title in lowercase with underscores (e.g., "CI Runs bun test" → "ci_runs_bun_test")

The file content must start with YAML frontmatter followed by the memory body:

```markdown
---
name: {{memory name}}
description: {{one-line description — used to decide relevance in future conversations}}
type: {{user|feedback|project|reference}}
---

{{memory body content}}
```

For feedback/project types, structure the body as: rule/fact, then a **Why:** line (the reason) and a **How to apply:** line (when/where this guidance kicks in).

**Step 2 — Update the MEMORY.md index**

After writing the memory file, use the Edit tool to add a one-line entry to `C:\Users\mey\.codeartsdoer\memory\C--Users-mey-Desktop-universalweb-api-main/MEMORY.md`:

```
- [{{Title}}]({{filename}}.md) — {{one-line hook}}
```

Keep MEMORY.md under 200 lines and 25KB. If it exceeds the limit, trim oldest entries.

## Before recommending from memory

A memory that names a specific function, file, or flag is a claim that it existed *when the memory was written*. It may have been renamed, removed, or never merged. Before recommending it:
- If the memory names a file path: check the file exists.
- If the memory names a function or flag: grep for it.
- If the user is about to act on your recommendation (not just asking about history), verify first.

## Memory vs. other persistence

- **Memory files** (`C:\Users\mey\.codeartsdoer\memory\C--Users-mey-Desktop-universalweb-api-main/`) — for durable cross-session context (user profile, feedback, project context, external references).
- **AGENTS.md** — for project conventions and coding guidelines that apply to the current project.
- **README.md** — for user-facing documentation and usage instructions.
- **CHANGELOG.md** — for version change logs.
- **Plans** — for implementation approach alignment within a conversation.
- **Tasks** — for tracking work progress within a conversation.

Use memory only for information that will be useful in future conversations and cannot be derived from the code or project files.
