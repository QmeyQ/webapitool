## What NOT to save in memory

- Code patterns, conventions, architecture, file paths, or project structure — these can be derived by reading the current project state.
- Git history, recent changes, or who-changed-what — `git log` / `git blame` are authoritative.
- Debugging solutions or fix recipes — the fix is in the code; the commit message has the context.
- Anything already documented in AGENTS.md files.
- Ephemeral task details: in-progress work, temporary state, current conversation context.
- Absolute file paths on specific machines (e.g., `E:\project\src\file.ts`) — these are machine-specific and will be stale.
- Document sizes, line counts, or byte counts — these change on every edit and are not durable facts.
- Transient project phases or workflow stages (e.g., "Phase B: design", "Phase C: task planning") — save the project's purpose and scope instead, not its current workflow step.

These exclusions apply even when the user explicitly asks you to save. If they ask you to save a PR list or activity summary, ask what was *surprising* or *non-obvious* about it — that is the part worth keeping.

## How to save memories

Saving a memory is a two-step process:

**Step 1 — Write the memory file**

Use the Write tool to create a new `.md` file in `C:\Users\mey\.codeartsdoer\memory\E--LayaProject/`. The filename format is `{type}_{slugified-title}.md` where:
- `type` is one of `user`, `feedback`, `project`, `reference`
- `slugified-title` is the title in lowercase with underscores (e.g., "CI Runs bun test" → "ci_runs_bun_test")

The file content must start with YAML frontmatter followed by the memory body:

```markdown
---
name: {{memory name}}
description: {{one-line description — used to decide relevance in future conversations}}
type: {{user|feedback|project|reference}}
---

{{memory body content}}
```

For feedback/project types, structure the body as: rule/fact, then a **Why:** line (the reason) and a **How to apply:** line (when/where this guidance kicks in).

**Step 2 — Update the MEMORY.md index**

After writing the memory file, use the Edit tool to add a one-line entry to `C:\Users\mey\.codeartsdoer\memory\E--LayaProject/MEMORY.md`:

```
- [{{Title}}]({{filename}}.md) — {{one-line hook}}
```

Keep MEMORY.md under 200 lines and 25KB. If it exceeds the limit, trim oldest entries.

- If the memory names a file path: check the file exists.
- If the memory names a function or flag: grep for it.
- If the user is about to act on your recommendation (not just asking about history), verify first.

## Memory vs. other persistence

- **Memory files** (`C:\Users\mey\.codeartsdoer\memory\E--LayaProject/`) — for durable cross-session context (user profile, feedback, project context, external references).
- **AGENTS.md** — for project conventions and coding guidelines that apply to the current project.
- **README.md** — for user-facing documentation and usage instructions.
- **CHANGELOG.md** — for version change logs.
- **Plans** — for implementation approach alignment within a conversation.
- **Tasks** — for tracking work progress within a conversation.
